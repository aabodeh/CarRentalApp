# PR 5 — retry queue (K2), My bookings + tabs (K3)

Branch `feat/sync-and-bookings` from main. Read AGENTS.md. Plan mode, wait for my OK.
This closes kernel NFRs K2 and K3. Deadline is Friday: implement the required minimum well rather
than a sophisticated queue badly. The design doc will state which depths we defer.

## 1. Bookings against the API
`bookingRepository` posts to the `bookings` resource. `clientBookingId` (already in the seed schema)
is the idempotency key: a retry that actually succeeded twice must not create two bookings. Bookings
persist locally first, always — the local write never depends on the network.

## 2. Retry queue (K2, minimum depth)
- Pending bookings live in the existing local store; the queue is derived from them, not a second
  source of truth.
- On failure: `syncStatus: 'failed'`, attempt count stored, retried with backoff (e.g. 2s, 8s, 30s,
  then stop and let the user retry by hand). Constants in one place, documented.
- Retry triggers: app foreground, network coming back (`useNetworkStatus`), and the timer.
  Never block the UI; a booking being retried stays usable in the list.
- Explicitly out of scope, say so in the code comment and tell me for the design doc: background
  retries while the app is closed, conflict resolution, and multi-device sync.

## 3. Sync transparency (K3)
- `SyncStatusBadge` already exists: use it everywhere a booking appears; never invent a second visual
  language for status.
- When a retry finally succeeds, the user must be told — the course requires the notification, not
  just a silently updated badge. Use an in-app toast/banner, announced to screen readers
  (`AccessibilityInfo.announceForAccessibility`). No push notifications.
- Failed bookings offer a manual "Try again".

## 4. My bookings screen + tabs
- Bottom tab navigator: "Cars" (the existing stack) and "My bookings". Typed navigation throughout;
  update `RootStackParamList`/param lists properly, no `any`.
- `MyBookingsScreen`: bookings newest first, each with car name, dates, total, and its sync badge.
  All four states (loading, empty with a route into the car list, error, offline). Reuse `StateView`.
- Booking success now routes here, so the user sees the status they were promised.
- Motion consistent with the rest: same durations and easings, reduce-motion respected.

## 5. Tests
Queue behaviour with fake timers: retry after a failure, backoff spacing, stop after the cap, success
after a retry marks completed and announces, idempotency key prevents duplicates, coming back online
triggers a retry, a pending booking survives a restart (store round-trip). Screen tests for all four
states and for navigation. Gherkin-named, per AGENTS.md.
