# PR 3 — car details, booking flow and BookingContext

Branch `feat/booking-flow` from main (PRs #4 and #5 are merged). Read AGENTS.md first. Plan mode,
wait for my OK. This is a big one: keep commits granular so it stays reviewable.

## 1. CarDetailsScreen
- Reads the `carId` route param, uses `useCar`, handles loading / error / not-found (not-found gets
  its own copy and a "Back to cars" action — a generic error would be wrong here).
- Editorial layout: large hero image, name as display type, price per day prominent, a spec grid
  (year, seats, transmission, fuel, location), availability.
- A sticky bottom bar with the primary "Book this car" action. It must stay clear of the home
  indicator (safe-area inset) and not cover the last line of content when scrolled to the bottom.
- Unavailable cars: the action is disabled with `accessibilityState.disabled`, and the reason is
  stated visibly, not only by colour.
- Motion: hero scales slightly on scroll, content sections stagger in, bottom bar slides up on mount.
  All gated on `useReducedMotion`. Header title fades in only once the hero name scrolls out of view.

## 2. BookingContext
`src/context/BookingContext.tsx` — the app's booking state, per AGENTS.md (context holds cross-screen
state; the repository owns the data).
- `bookings: Booking[]`, `createBooking(input): Promise<Booking>`, plus state for in-flight creation.
- Backed by a new `src/repositories/bookingRepository.ts` (in-memory for now, same seam as cars, same
  simulated latency; the API and the retry queue replace its internals in the next PR).
- New bookings get `syncStatus: 'pending'` and settle to `'completed'` — this is the K3 seam and the
  next PR turns it real. Do not build the retry queue here.
- Provider mounted in App.tsx. Unit-test the reducer/logic without rendering screens.

## 3. BookingScreen
- Form: renter name, renter email, start date, end date. Use plain `TextInput`s from react-native for
  the text fields; for dates pick the lightest option that works on both platforms and say which you
  chose and why (a dependency needs a reason, per AGENTS.md).
- Live summary: day count and total price via our existing utils, updating as dates change. Show the
  same-day-is-one-day rule in the copy, not just in code.
- Validation on submit, with errors tied to their field and announced accessibly: name non-empty,
  email shaped like an email, end date not before start date, no dates in the past.
- Submit → creates the booking, shows a success state with its sync status, and offers "Back to cars".
  Disable the submit button while in flight; never allow a double submit.
- Keyboard handling: `KeyboardAvoidingView` + `keyboardShouldPersistTaps`, so the submit button is
  reachable with the keyboard open on both platforms. Test this — it is the classic RN bug.

## 4. Navigation
Type `Booking: { carId: string }` in `RootStackParamList`. Details → Booking passes the carId.
Titles come from the screen options, not from ad-hoc headers.

## 5. Tests
Screens and context, Gherkin-named as always. Cover: details renders a car, details handles a missing
car, the book action is disabled when unavailable, the form rejects each invalid case, the total
updates when dates change, submitting creates a booking with pending status, double submit creates one
booking. Test behaviour through the UI, not implementation details.

## 6. Accessibility
Every input has a visible label and an `accessibilityLabel`; error text is associated with its field;
44pt targets; 200% text must not clip the summary or the bottom bar.
