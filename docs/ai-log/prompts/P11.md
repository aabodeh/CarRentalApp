## Why this PR
The app works but looks thin. This adds visual depth and two genuinely useful features — it is not a
restyle. Do NOT redefine the design tokens: the palette, type scale, spacing, radii and motion in
`src/theme/` are measured and audited. Use them harder instead (more hierarchy, better density,
more considered empty states), and say in the plan if a token is genuinely missing.

## 1. Tab bar, properly
Four tabs with icons — `@expo/vector-icons` ships with Expo, so no new dependency:
- **Cars** — the existing stack
- **Saved** — favourited cars
- **Bookings** — the existing My bookings, keeping its pending counter
- **Profile** — new
Custom tab bar styling consistent with the design language: active state carried by more than colour
alone (weight or an indicator), labels kept for accessibility, ≥44pt targets, safe-area aware.

## 2. Data model additions (these go in the design doc, so keep them minimal and justified)
- `UserProfile` — `name`, `email`, `preferredLocation?`. Local to the device, no account, no auth.
  Persisted through the existing versioned store (bump the storage version, migrate or discard as you
  did before).
- Favourites — a persisted set of car ids. Not a new entity if a `string[]` is honest; say which you
  chose and why.
Write both into `docs/requirements-coverage.md` and list them in the PR description as new FE/US
candidates, so the design doc can be updated in step.

## 3. Profile screen
- Edit name and email, saved locally, with the same validation as the booking form (reuse it, do not
  duplicate the rules).
- These prefill the booking form — that is the point of the feature, and a real fix for having to
  retype details on every booking. The form stays editable.
- Small stats from real data only: bookings made, upcoming booking, favourites count. No invented data.
- Somewhere honest about what this is: a note that the profile lives on this phone only, no account.
- Include a reduce-motion-safe entrance consistent with the other screens.

## 4. Favourites
- A heart control on `CarCard` and on details, with haptic feedback and a spring, respecting
  reduce-motion. `accessibilityLabel` reflecting state ("Save Tesla Model 3" / "Remove from saved"),
  and `accessibilityState.selected`.
- Saved tab: same card component, its own empty state that routes into Cars.
- A favourited car that disappears from the API must not break the Saved list — decide the behaviour
  and state it.

## 5. Car list depth
- Search by make/model, debounced, with a clear control and an accessible label.
- Filter chips for fuel and transmission, multi-select, showing the result count.
- A "no results" state distinct from the empty state, with a way to clear filters.
- Filters are UI state only — do not push them into the repository or the cache.

## 6. Visual polish pass
Go through every screen for hierarchy, spacing rhythm and density. Improve empty and error states so
they look designed rather than defaulted. Keep motion consistent with `src/theme/motion.ts` and never
add a duration or easing inline.

the plan rather than editing it quietly. Re-check 200% text on the new screens.
